# Модель симуляції AdLab

> **Це навчальна модель, а не реконструкція алгоритмів Meta.** Вона відтворює причинно-наслідкові зв'язки, які таргетолог має розуміти: аукціон і CPM, воронку від показу до продажу, втрати трекінгу, атрибуцію, навчальну фазу, вигорання креативів. Усі числові параметри (CPM за країнами, базові CTR/CVR, частки інвентарю, коефіцієнти) — припущення, підібрані для правдоподібних навчальних патернів. Їх не можна використовувати як прогноз реальних результатів.

Код: `src/simulation/*`. Тести формул: `tests/unit/metrics.test.ts`, `engine.test.ts`, `scenarios.test.ts`.

## 1. Загальна схема дня

`simulateOneDay(account)` (`engine.ts`) — чиста функція. Кроки:

1. **Перевірка оголошень.** Кожне оголошення зі статусом `in_review` проходить `reviewAd()`. Результат: `active` або `rejected` з причинами. Кампанії й набори `in_review` стають `active`.
2. **Відбір доставки.** Беруться активні кампанії → активні набори в межах розкладу → оголошення зі статусом `active` і схваленою перевіркою. Набір без жодного такого оголошення не доставляється.
3. **Модель набору.** `buildAdSetModel()` (`model.ts`) рахує очікувані значення без шуму: аудиторію, мікс плейсментів, CPM, CTR оголошень, частку LPV, CVR сесії, очікувані результати на $1.
4. **Розподіл бюджету** між наборами кампанії (розділ 7).
5. **Доставка набору.** `simulateAdSetDay()` додає шум із seeded RNG, рахує покази, кліки, сесії, реальні та звітні конверсії й записує рядок `DailyMetrics` на кожне оголошення.
6. **Навчальна фаза** оновлюється за подіями оптимізації, що «проявилися» цього дня (розділ 8).
7. **Журнал змін:** результати перевірки, зміни фази навчання, підсумок дня.

`simulateDays(n)` повторює це n разів і зберігає запис запуску (`runs`).

### Детермінованість

`createRng(account.seed, "adset" | "ad", entity.seq, day)` — FNV-хеш ключа → mulberry32. Розподіли: рівномірний, нормальний (Box–Muller), мультиплікативний шум `noise(σ)`, Пуассон, біноміальний (сума проб Бернуллі для n ≤ 60, нормальне наближення для більших n). Однаковий стан акаунта та дії дають однакові результати.

## 2. Аудиторія (`audience.ts`)

`estimateAudience()` повертає:

- **size** — потенційний розмір:
  - ручна аудиторія: `гео × мова × вік × стать × частка інтересів` (частка інтересів = `1 − Π(1 − share_i)`, тобто об'єднання);
  - з custom/lookalike: `Σ розмірів × вік × стать × інтереси`, але не більше демографічної бази;
  - **Advantage+ audience:** інтереси й аудиторії — підказки, вони не звужують розмір. Жорсткі лише контролі: гео, мінімальний вік, мова, виключення;
  - виключення зменшують розмір не більш ніж на 50%.
- **relevance** (0.5..1.9) — наскільки аудиторія відповідає оферу:
  - ручна: `ageFit × interestFit × (1 + 0.7·customIntent)`, де `ageFit` — частка «ядрового» віку вертикалі у вибраному діапазоні, `interestFit = 0.85 + 0.12·релевантні − 0.1·нерелевантні інтереси`;
  - Advantage+: `0.9 + бонус підказок + 0.18·прогрес навчання` (при конверсійній меті). Алгоритм поступово знаходить релевантних людей.
- **intent** — схильність до дії: `max(0.25, intent custom-аудиторії)`, з Advantage+ ×0.6. Ретаргетинг має intent ≥ 0.6.
- **fit** — відповідність аудиторії бізнесу (`ageFit × interestFit` для ручної). Впливає на CVR.

**Ефективна аудиторія** (активна за тиждень): `A_eff = max(500, size × 0.62)`.

**Охоплення** як насичувальна функція показів:

```
R = A · (1 − e^(−I / (φ·A))),   φ = 1.25
```

Через це частота природно зростає, коли бюджет завеликий для аудиторії. Денне охоплення рядка: `imp / (1.08 + 0.3·min(3, imp/A_eff))`. Кумулятивне охоплення набору рахується за формулою вище в знімках набору. Охоплення в звітах **не сумується**: його оцінюють з показів.

**Обмеження:** охоплення різних наборів сумується без урахування перетину аудиторій. `audienceOverlap()` використовується лише для попереджень.

## 3. Плейсменти (`model.ts → placementMix`)

Кожен плейсмент у `catalog.ts` має: `inventory` (частку інвентарю), `cpm`, `ctr`, `lpvQuality` (частку кліків, що доходять до сторінки) і `cvrQuality` (якість трафіку для конверсії).

Цінність плейсменту залежить від цілі:

| Ціль | Цінність |
|---|---|
| reach / impressions | `1 / cpm` |
| відео | `(1.3 для Reels/Stories) / cpm` |
| link_clicks | `ctr / cpm` |
| landing_page_views | `ctr · lpvQuality³ / cpm` |
| конверсійні | `ctr · lpvQuality^3.5 / cpm` |

Частка = `inventory × цінність^e`, де `e = 0.85` для Advantage+ placements (система активно оптимізує) і `0.5` для ручних плейсментів. При Advantage+ частка Audience Network обмежена 30% для всіх цілей, крім link_clicks. Тому оптимізація під кліки може «йти» в AN: це навчальний патерн дешевих, але неякісних кліків.

**Відповідність медіа плейсменту** (`assetFitForPlacement`): рекомендоване співвідношення сторін → 1.0, 16:9 у неприйнятному плейсменті → 0.55, інше → 0.72; статичне зображення в Reels додатково ×0.75. Для Stories/Reels використовується вертикальна версія медіа, якщо її додано.

## 4. Креатив (`creative-quality.ts`)

Евристична оцінка 0..1:

```
quality = 0.36·hook + 0.2·placementFit + 0.14·copy + 0.1·headline + 0.1·CTA + 0.1·(0.5 + 0.5·messageMatch)
```

- **hook** — сила медіа з бібліотеки або дефолт для завантаженого (відео ≤ 60 с: 0.68, довше: 0.55, зображення: 0.6).
- **copy / headline** — довжина та частка великих літер.
- **CTA** — відповідність кнопки цілі кампанії.
- **messageMatch** — частка ключових слів оферу посадкової сторінки (за коренем), присутніх у тексті.

Множники:

```
ctrMultiplier         = (0.45 + 1.15·quality) · (1 + 0.05·min(clickbait, 2)) · (1.03 при creative enhancements)
cvrMultiplier         = (0.62 + 0.55·match) · (0.85 при ≥ 2 клікбейт-фразах)
leadQualityMultiplier = (0.8 + 0.3·match) · (0.7 | 0.9 | 1 залежно від клікбейту)
```

Клікбейт підвищує CTR, але знижує конверсію та якість лідів. Цей компроміс користувач має побачити в даних.

**Розподіл показів між оголошеннями** набору: `w_i ∝ exp(4 · quality_i · fatigue_i)` з мінімальною часткою `0.08/n`. В A/B тесті креативів розподіл рівний.

## 5. Аукціон і CPM

```
CPM = baseCPM_geo × competition_vertical × GOAL_CPM[goal] × sizeFactor
      × placementMix.cpm × (1.25 − 0.45·avgQuality) × saturation
      × learning (1.08 у навчанні) × special (1.05 для спецкатегорій)
      × weekday × marketEvents × noise(7%)
```

- `baseCPM_geo` — середнє CPM країн, зважене за досяжною аудиторією (місто з радіусом має вагу 0.3).
- `sizeFactor = clamp(1 + 0.18·log10(1M / size), 0.85, 1.9)`: вузька аудиторія коштує дорожче.
- `saturation = 1 + 0.12·max(0, freq₁₄ − 2)`: частота набору за 14 днів.
- `GOAL_CPM`: reach 0.7 … conversion_value 1.4 (оптимізація під дорожчі події конкурує за «цінніших» користувачів).
- `weekday`: Нд 0.96, Пн 1.02, Вт 1.0, Ср 1.0, Чт 1.02, Пт 0.98, Сб 0.95.
- `marketEvents` — механізм сценарних подій ринку (день + множник CPM + назва). Рушій його підтримує, але поточні сценарії місій його не використовують.

Покази: `imp = spend / CPM × 1000`, обмежені інвентарем (розділ 7).

## 6. Воронка

### Кліки

```
CTR_ad = baseCTR_vertical × ctrMultiplier × √relevance × ctrMix_placements × fatigue × GOAL_CLICK_BIAS[goal]
```

`GOAL_CLICK_BIAS` відображає, кого система шукає: link_clicks 1.35 («клікери»), reach 0.72, thruplay 0.65.

| Метрика | Як рахується | Чим відрізняється |
|---|---|---|
| **Clicks (all)** | link clicks + кліки по профілю, «ще», реакції: `Bin(imp, 0.006 + 0.01·hook)` | Включає взаємодії, що не ведуть з платформи |
| **Link clicks** | `Bin(imp, CTR_ad · noise(8%))` | Кліки, що мали вести до місця призначення |
| **Outbound clicks** | `Bin(webClicks, 0.94)` | Лише кліки, що вивели з платформи на сайт |
| **Сесії** (реальні) | `Bin(outbound, LOAD_SPEED × lpvQualityMix × (0.85 якщо не mobile-friendly))` | Люди, що дочекалися завантаження сторінки |
| **Landing page views** | `Bin(сесії, 0.9 × згода)` за наявності Pixel з PageView | Сесії, зафіксовані Pixel |

`LOAD_SPEED`: fast 0.9, average 0.8, slow 0.55. Якщо домен URL не збігається з доменом сайту акаунта, частка сесій 2% (зламане посилання).

### Конверсії на сайті

```
sessionCVR = baseCVR_site × (0.7 + 0.9·intent) × fit^0.8 × cvrMultiplier × cvrQualityMix
             × alignment × learningFactor × (√purchasingPower для покупок)
```

- **alignment** — наскільки ціль оптимізації відповідає основній конверсії сайту. 1.0 для оптимізації під саму подію; ViewContent 0.62; LPV 0.45; link clicks 0.3; без видимої події 0.45. Тому оптимізація під кліки дає дешевий трафік, але мало лідів.
- **learningFactor**: active 1.05, learning_limited 0.82, learning 0.88 + 0.12·прогрес.
- Сайт генерує лише свою основну конверсію (`landingPage.primaryConversion`): магазин — покупки, школа — ліди.

Реальні конверсії: `Bin(сесії, sessionCVR · noise(12%))`.

### Інші місця конверсії

- **Миттєві форми:** заповнення = кліки × частка форми × (0.24 стандартна / 0.15 higher intent) × `max(0.6, 1 − 0.05·(питань − 3))` × (0.85 + 0.3·intent). Кожне питання понад 3 підвищує якість лідів форми на 4% (до +20%).
- **Повідомлення:** розмови = 55% кліків, з них 18% стають лідами.
- **Дзвінки:** 40% кліків, 30% стають лідами.
- **Застосунок:** встановлення = 28% кліків, якщо застосунок зареєстровано; app events = 25% встановлень.

### Відео й залучення

- 3-секундні перегляди: `Bin(imp, (0.15 + 0.3·hook) × 1.4 при відео-цілі)`.
- ThruPlay: 55% переглядів для відео ≤ 15 с, 40% для ≤ 30 с, 22% для довших.

## 7. Бюджети та ставки

### Розподіл

- **Бюджет кампанії (Advantage+ campaign budget):** денний бюджет ділиться пропорційно `resultsPerDollar^1.2` з мінімальною часткою `0.1/n` на набір. Довічний бюджет: `(budget − spent) / днів_до_кінця`. В A/B тесті з бюджетом кампанії розподіл рівний.
- **Бюджет наборів:** кожен набір витрачає свій бюджет. **Budget sharing:** набори з ефективністю нижче медіани віддають 20% свого бюджету наборам вище медіани.
- **Пейсинг:** фактичні витрати 90–100% бюджету (`N(0.97, 0.02)`).
- **Обмеження:** витрати ≤ інвентар (`A_eff × 0.9` показів на день або ліміт частоти), ≤ залишок віртуального балансу акаунта. Чутливий таргетинг множить цільові витрати на 0.4 (розділ 13).

### Стратегії ставок

| Стратегія | Модель |
|---|---|
| Highest volume / highest value | Без обмежень |
| Cost per result goal | Якщо ціль < прогнозованої вартості: доставка × `(ціль/прогноз)³` (не менше 3%) |
| Bid cap | Якщо cap < 0.8 × прогнозованої вартості: доставка × `ratio⁴` (не менше 1%), бюджет недовитрачається |
| ROAS goal | Якщо ціль > досяжного ROAS: доставка × `(досяжний/ціль)³` |

Кожне обмеження додає пояснення в примітки дня, щоб користувач бачив причину недовитрати.

## 8. Навчальна фаза (`learning.ts`, `operations.ts`)

За довідкою Meta: набір зазвичай виходить з навчання після ~50 подій оптимізації за 7 днів після останнього суттєвого редагування.

- `not_started → learning` у перший день доставки.
- `learning → active`, коли сума подій за ковзні 7 днів ≥ 50.
- `learning → learning_limited`, якщо минуло ≥ 7 днів або з 3-го дня прогноз на 7 днів < 35 подій.
- Події оптимізації рахуються з урахуванням затримки та вікна атрибуції: конверсія, що «доїде» завтра, зарахується завтра.

**Скидання** (`resetLearning`, лічильник `resets`), як і в довідці «Last significant edit»:

- набір: зміна аудиторії, плейсментів, місця конверсії, цілі ефективності, події оптимізації, стратегії ставок, суми ставки або ROAS goal;
- кампанія: зміна стратегії ставок, суми ставки, ROAS goal або рівня бюджету — скидає всі набори кампанії;
- зміна бюджету (набору або кампанії) більш ніж на 20%. **Поріг 20% — припущення симулятора** (`SIGNIFICANT_BUDGET_CHANGE`), Meta не публікує точного значення;
- додавання оголошення в набір або зміна креативу оголошення;
- відновлення набору після паузи ≥ 7 днів.

Скидання відбувається лише для опублікованих сутностей. Зміни чернетки на навчання не впливають.

Вплив фази: CPM ×1.08 у навчанні, CVR ×(0.88…1.05), а також прогрес Advantage+ audience.

## 9. Вигорання (`fatigueFactor`)

```
freq₁₄    = imp₁₄ / R(imp₁₄, A_eff)                  частота оголошення за 14 днів
tolerance = 2.0 + 0.25·min(4, різних_медіа − 1)       різноманітні креативи → вища толерантність
freqF     = 1 / (1 + 0.22·max(0, freq₁₄ − tolerance))
ageF      = max(0.78, 1 − 0.006·max(0, вік_днів − 10))
fatigue   = freqF × ageF
```

Fatigue множить CTR і вагу оголошення в ротації. Разом із `saturation` у CPM це дає класичний патерн: частота ↑ → CTR ↓ → CPM ↑ → CPL ↑.

## 10. Трекінг (`tracking.ts`)

Яка частка **реальних** подій потрапляє в датасет:

```
browser = 0.8 × згода           якщо подія налаштована в Pixel; ×2, якщо браузер шле її двічі
server  = 0.92 × згода          якщо CAPI увімкнено (Purchase і Lead надсилаються завжди)

з event_id:  capture = 1 − (1 − min(1, browser))·(1 − server) + max(0, browser − 1)   (дедуплікація між джерелами)
без event_id: capture = browser + server                                              (подвійний рахунок)

match        = CAPI ? min(0.97, 0.8 + 0.017·EMQ) : 0.8
reportedRate = capture × match
```

`згода = acceptRate`, якщо увімкнено банер згоди, інакше 1.

Дедуплікація **не** діє всередині одного джерела: дубль браузерної події лишається навіть з event_id. Так моделюється кейс «у кабінеті покупок більше, ніж у бекенді» (Error Lab e05).

## 11. Атрибуція та звітність (`engine.ts`, `reporting.ts`)

Рушій зберігає «сирі» дані:

- **click-through**: масив за днями затримки `clickLeads[k]`, `clickPurchases[k]`, `clickValue[k]` (k = 0…6). Звітні конверсії `Poisson(real × reportedRate)` розподіляються мультиноміально за лаг-профілем:
  - ліди `LEAD_LAG = [0.70, 0.15, 0.07, 0.04, 0.02, 0.01, 0.01]`;
  - покупки (e-commerce) `[0.55, 0.18, 0.10, 0.07, 0.05, 0.03, 0.02]`;
  - покупки (інші вертикалі) `[0.42, 0.20, 0.12, 0.10, 0.07, 0.05, 0.04]`;
- **view-through**: `Poisson(real × (0.12 + 0.25·intent + 0.05 для відео) × reportedRate)`;
- **engage-through**: `Poisson(real × 0.05 × reportedRate)`.

Звітні значення рахуються **під час запиту** (`rowConversions`):

```
leads = Σ_{k ≤ min(clickWindow − 1, днів_що_минули)} clickLeads[k]
        + viewLeads   (якщо 1-day view увімкнено)
        + engageLeads (якщо 1-day engage-through увімкнено)
```

- Конверсії зі «свіжих» днів ще можуть дорахуватися. Звіт позначається `incomplete`, а UI показує попередження.
- Перемикання вікна атрибуції в Analytics перераховує звіт без нової симуляції. Доступні пресети: 1-day click, 7-day click, 7-day click + 1-day view, 7-day click + 1-day engage-through + 1-day view.
- **Інкрементальність:** лише 25% view-through конверсій вважаються реальними додатковими конверсіями (решта сталася б і без реклами). Тому реальні дані бізнесу менші за суму атрибутованих.

## 12. CRM — «правда» бізнесу

На кожен рядок рушій також записує дані, недоступні рекламному кабінету:

- `trueLeads`, `truePurchases`, `trueRevenue` — реальні події, включно з інкрементальними view-through.
- `qualifiedLeads` — `Bin(trueLeads, qualRate)`, де:

  ```
  qualRate = sourceMix × (0.75 + 0.5·intent) × leadQualityMultiplier
             × 1.35 (conversion leads + CRM feedback)
             × 0.85 (alignment < 0.5)
             × 1.15 (кваліфікаційне питання у формі)
  ```

  `sourceMix` — середня якість за джерелами: сайт 0.42, форма 0.2 (higher intent 0.34), повідомлення 0.35, дзвінки 0.5.
- `crmAttributedLeads` — скільки лідів CRM може приписати Meta. Без UTM лише 12% лідів із сайту, з UTM — 93%. Для покупок: 10% і 90%.

Через це Analytics показує розбіжність «Meta vs CRM» і вартість **кваліфікованого** ліда. Окремо там показано бізнес-ROAS (`trueRevenue / spend`) поруч з атрибутованим ROAS.

## 13. Перевірка оголошень (`review.ts`)

Правила застосовуються до тексту оголошення (Unicode-aware регулярні вирази, працюють з кирилицею) і до налаштувань.

| Код | Підстава | Результат |
|---|---|---|
| `unrealistic_claims` | «гарантований дохід», «схуднення за N днів» тощо | reject |
| `personal_attributes` | Звертання, що стверджує особисту характеристику («Ви страждаєте від…?») | reject |
| `before_after` | «до і після» разом зі схудненням / «мінус N кг» | reject |
| `special_category_missing` | Ознаки кредиту, вакансії, оренди/продажу житла без оголошеної спецкатегорії | reject |
| `siep_eu` | Соціальні питання / вибори / політика з таргетингом на ЄС | reject |
| `siep_authorization` | SIEP поза ЄС: навчальний акаунт не має авторизації рекламодавця | reject |
| `invalid_url` / `non_functional_landing` | Некоректний URL або домен не відповідає сайту | reject |
| `lead_form_privacy` | Миттєва форма без політики конфіденційності | reject |
| `sensitive_targeting` | Інтереси, що натякають на здоров'я, фінансовий стан тощо | limit: оголошення схвалюється, але доставка ×0.4 (припущення симулятора) |

Правила спрощені та охоплюють лише частину Advertising Standards. Кожне має посилання на статтю бази знань.

## 14. Валідація (`validation.ts`)

Три рівні:

- **error** блокує публікацію. Приклади: немає назви, бюджет нижче мінімуму, lifetime-бюджет без дати завершення, конверсійна ціль без Pixel або без події оптимізації, несумісна стратегія ставок, A/B тест без двох варіантів, порушення правил спецкатегорії (вік, стать, lookalike, радіус), аудиторія з ознаками здоров'я/фінансів, порожня аудиторія, немає медіа, URL без `https://`, миттєва форма без політики конфіденційності.
- **warning** — ризик для результату: розпорошений бюджет, перетин аудиторій наборів, прогноз < 50 подій за 7 днів (ймовірний Learning limited), подія не надходить у датасет або дублюється, немає PageView для LPV, Conversion leads без CRM, мала аудиторія, ЄС без банера згоди, Audience Network + оптимізація на кліки, чутливий інтерес, немає UTM, A/B тест без гіпотези.
- **info** — підказка: мало плейсментів, заголовок довший за 40 символів, немає вертикальної версії для Stories/Reels, плейсмент зі статусом Needs Review.

`validateCampaignTree()` збирає всі рівні для діалогу публікації з посиланням на поле.

## 15. Діагностика (`diagnostics.ts`)

`diagnose(account, rows)` повертає знахідки. Кожна має докази (числа), **альтернативні пояснення**, **наступний тест**, рівень упевненості з поясненням і статтю.

Правила: високий CPM, низький CTR, дорогий клік, кліки без LPV, низька якість лідів (CRM), немає покупок, ROAS на малій вибірці, вигорання (частота > 3 і падіння CTR > 15% між першими й останніми 4 днями), недостатньо даних (< 15 конверсій), розбіжність з CRM, подвійний рахунок, learning limited, тренд CTR.

Статистика (`metrics.ts`):

- `wilsonInterval` — довірчий інтервал для CTR/CVR;
- `twoProportionZTest` — порівняння креативів;
- `dataSufficiency`: < 15 конверсій — недостатньо, 15–49 — орієнтовно, ≥ 50 — надійно.

Усі формули метрик використовують `safeDiv` і повертають `null` замість `Infinity`/`NaN`. UI показує «—».

## 16. Оцінювання (`scoring/`)

### Місії: Skill Score 0–100

Бал складається з трьох джерел, кожне розподілено за 10 вимірами (ціль, структура, аудиторія, бюджет, трекінг, креатив, метрики, оптимізація, політики, аргументація):

1. **Рубрика процесу:** перевірки стану акаунта (`scoring/checks.ts`). Наприклад: «кампанія з ціллю Leads, оптимізація під Lead, ≥ 2 оголошення, UTM на всіх оголошеннях, ≥ 5 днів доставки, CPL ≤ KPI». Деякі пункти критичні.
2. **Питання:**
   - вибір: для multi `(TP − 0.75·FP) / |correct|`;
   - число: ±5% — повний бал, ±15% — половина;
   - текст: евристика `0.35·довжина + 0.65·покриття ключових понять`.
3. **Кейс для портфоліо** — евристика за ключовими поняттями (10 балів аргументації).

**Захист від вгадування:**

- Питання з вибором, прив'язане до питання-доказу, без обґрунтування дає ≤ 50% свого балу.
- Висока впевненість у хибній відповіді: −25% балу питання.
- Аргументація < 35 → загальний бал ≤ 75.
- Будь-яка критична помилка → бал ≤ 69 (поріг зарахування 70).

Еталонні числові відповіді рахуються з того самого акаунта, з яким працював користувач (`asOfHandover` — на момент передачі сценарію). Тому вони не залежать від того, скільки днів користувач симулював після цього.

### Error Lab

```
score = 55·причини + 25·докази + 20·пояснення − калібрування
причини = max(0, (правильні − 0.75·хибні) / усі_правильні)
докази  = max(0, (релевантні − 0.5·нерелевантні) / усі_релевантні)
калібрування: −10 за високу впевненість при неточному діагнозі; −5, якщо дані кейсу не дозволяють високої впевненості
```

## 17. Відомі спрощення

- Немає моделі конкурентів в аукціоні та ставок інших рекламодавців: конкуренція — множник вертикалі.
- Advantage+ audience моделюється як розширення аудиторії, що зростає з прогресом навчання, а не як окремий алгоритм.
- Перетин аудиторій між наборами не зменшує охоплення.
- Опрацювання тексту оголошень — регулярні вирази, а не класифікатор.
- Оцінка аргументації — ключові слова, а не розуміння змісту.
- Відео зберігається як постер + тривалість; «hook» завантаженого медіа — константа.
- Opportunity score, Aggregated Event Measurement-ліміти, A/B тести з Brand Lift не моделюються.
